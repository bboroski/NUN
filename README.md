# NUN — Minimal Kernel Substrate

**Репозиторій-специфікація для мінімального системного ядра.**

Поточний стан: **каркас документації**. У репозиторії є лише README; вихідного коду ядра, boot path, linker script, build system, драйверів і тестів ще немає. Цей документ фіксує технічний напрям і не видає заплановані компоненти за реалізовані.

## Запропоновані межі системи

- **Boot contract:** формат handoff від завантажувача, карта пам'яті та версія ABI.
- **Architecture layer:** CPU entry, privilege transition, exception та interrupt vectors.
- **Memory layer:** фізичні сторінки, ранній allocator, віртуальна адресація й захист.
- **Execution layer:** task/context model і явна модель синхронізації.
- **Device boundary:** описані bus/driver interfaces без припущень про конкретну плату.
- **Diagnostics:** ранній serial/framebuffer output і структурований panic record.

## Інженерні вимоги

Кожна апаратно-залежна дія має бути прив'язана до конкретної архітектури й boot protocol. ABI, межі пам'яті, alignment, privilege level та interrupt policy мають бути задокументовані. Host-тести не можуть замінити емуляцію або перевірку на цільовій платформі.

## Поточна перевірка

Збірки та тестів поки немає: реалізація не створена. Перший кодовий етап має додати reproducible build, linker map, serial smoke test і автоматизовану перевірку образу.

## Технічна ідентичність

**NUN** — канонічне технічне ім'я мінімального kernel substrate. GitHub-шлях збережено лише як адресу репозиторію.

## Статус

Не використовувати як bootable OS і не завантажувати на фізичне обладнання: реалізованого ядра ще немає.
## Багатошарова автономність і взаємоінтеграція

NUN визначає системний шар екосистеми, але не поглинає інші проєкти та не вимагає їхньої присутності для роботи майбутнього ядра.

| Шар | Відповідальність | Інтеграційний контракт |
|---|---|---|
| NUNLauncher | Перевірка образу та передача boot context | NUN boot-information ABI |
| NUN | Архітектурний entry, пам'ять, виконання та захист | Версійовані kernel interfaces |
| Kloz | Переносні platform operations і caller-owned memory | Опційний platform adapter |
| CO | Життєвий цикл компонентів | Опційний lifecycle adapter |
| SaintSI | Спостереження за поступом і цілісністю даних | Опційний assurance adapter |
| ReaperCripple | BSP, fixtures та виробнича кваліфікація | Профілі конкретної плати |
| SAMBU | Мова, інструментарій і моделювання | Маніфести та схеми |
| Klipot | Каталог, граф зв'язків і операторська панель | Лише метадані; не runtime-залежність |

Інтеграція виконується через оголошені версії ABI та адаптери. Відсутність необов'язкового модуля не повинна ламати автономне ядро. Непідтверджена сумісність відображається як unknown, а не як успішна.

## Оновлення та відновлення

Залежності й GitHub Actions перевіряються Dependabot щотижня. Оновлення надходять окремими pull request і проходять контрактний CI. Автоматичне злиття та автоматичне встановлення вимкнені.

Майбутні kernel/boot artifacts мають проходити перевірку походження, підпису, сумісності, цілісності та recovery path до активації. Оновлення boot chain не може виконуватися без явного підтвердження оператора та перевіреного способу відновлення. Це політика майбутньої реалізації, а не заява про наявність готового updater.
