# NUN — Minimal Kernel Substrate

**NUN — операційна система з власним ядром, завантажувальним контрактом, системним ABI та користувацьким середовищем.**

Поточний стан: **ранній x86-64 boot foundation**. Додано Limine handoff, COM1-діагностику, framebuffer-маркер, початковий allocator фізичних сторінок і smoke-перевірки native-контрактів Kloz, CO, SaintSI та supervisor із ReaperCripple. Це ще не повна чи production-ready ОС: планувальник, user mode, драйверна модель, VFS, мережа, secure boot і графічна оболонка не реалізовані.

## Запропоновані межі системи

- **Boot contract:** формат handoff від завантажувача, карта пам'яті та версія ABI.
- **Architecture layer:** CPU entry, перехід між рівнями привілеїв, exception та interrupt vectors.
- **Memory layer:** фізичні сторінки, ранній allocator, віртуальна адресація й захист.
- **Execution layer:** task/context model і явна модель синхронізації.
- **Device boundary:** описані bus/driver interfaces без припущень про конкретну плату.
- **Capability composition layer:** реєстр можливостей, перевірка сумісності, побудова композицій, ізольоване підключення та атомарне повернення до попереднього стану.

## Об'єднання та поглинання можливостей

NUN має отримати **Capability Composition & Assimilation** — системний механізм, який дозволяє приймати нові модулі, перевіряти їхні контракти та залежності, поєднувати сумісні можливості в складені можливості й повторно використовувати ці композиції як звичайні модулі.

Це не безконтрольне злиття виконуваного коду. Кожна можливість має версіонований маніфест, ідентифікатор, ABI, перелік інтерфейсів і мінімально необхідних дозволів. Підключення проходить через карантин, перевірку, розв'язання конфліктів, ізольоване тестове середовище та транзакційну активацію.

## Інженерні вимоги

Кожна апаратно-залежна дія має бути прив'язана до конкретної архітектури й boot protocol. ABI, межі пам'яті, alignment, privilege level та interrupt policy мають бути задокументовані. Host-тести не можуть замінити емуляцію або перевірку на цільовій платформі.

Для системи композиції додатково обов'язкові: детерміноване розв'язання залежностей, відхилення циклічних залежностей, ізоляція модулів, принцип найменших привілеїв, походження артефактів, атомарна активація та перевірений rollback.

## Поточна перевірка

Композиція можливостей залишається архітектурним напрямом і не є завершеним runtime. Наявні boot-файли та native-контракти описані в розділі нижче. Host-тести й CI мають бути фактично виконані перед твердженням про готовність.

## Технічна ідентичність

**NUN** — канонічне технічне ім'я мінімального kernel substrate. GitHub-шлях збережено лише як адресу репозиторію.

## Статус

Це ранній boot image для розробки та тестування в QEMU. Він не є production-ready системою і не має встановлюватися на основний пристрій. Фізичне обладнання потребує окремої перевірки boot chain, драйверів, пам'яті та відновлення.

## Реалізована основа та збірка

Поточна гілка розробки додає завантажуваний kernel ELF для x86-64, перевірку обов'язкових Limine responses, serial-діагностику, чорно-жовтий framebuffer-маркер, монотонний allocator сторінок і перевірки інтегрованих C11-контрактів.

~~~bash
make deps
make check
make kernel
make iso
make run
~~~

Потрібні GCC/Clang x86-64, GNU Make, curl, git, xorriso та QEMU. CI налаштовано на host-тести, компіляцію ядра й перевірку ELF; факт проходження CI або запуску на фізичному пристрої не заявляється до появи відповідних звітів.

## Мовне середовище

Fortran, Pascal і Delphi/Object Pascal плануються як повноцінні user-space toolchains, runtime/RTL та SDK поверх стабільного C ABI. Це включає Fortran module/array/ISO_C_BINDING-профіль, Pascal units/classes/generics/exceptions і Delphi-mode compatibility/migration tooling. Вони не виконуються в ring 0 і не можуть обходити системний ABI.
